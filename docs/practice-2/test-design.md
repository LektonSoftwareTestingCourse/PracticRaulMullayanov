# Практика 2 — тест-дизайн и баг-репорты

## 1. Область тестирования

Проверяются авторизация, лимиты и баланс в Authorization Service; операции с картами в Card Management Service (CMS).

Основания: [ТЗ Authorization](../../tz/04-authorization.md), [ТЗ CMS](../../tz/05-card-management.md), [API-контракт](../api-spec.md), [OpenAPI](../api/openapi.yaml).

Результаты прогона: [test-results.md](test-results.md).

## 2. Классы эквивалентности

### 2.1. Статус карты

| ID | Класс | Валидность для авторизации | Ожидаемый результат |
|---|---|:---:|---|
| EC-STATUS-01 | `ACTIVE`, срок действия не истёк | Валидный | Продолжить проверку лимитов и баланса |
| EC-STATUS-02 | `INACTIVE` | Невалидный | `DECLINED`, `CARD_INACTIVE`, код `05` |
| EC-STATUS-03 | `BLOCKED` | Невалидный | `DECLINED`, `CARD_BLOCKED`, код `05` |
| EC-STATUS-04 | `EXPIRED` | Невалидный | `DECLINED`, `CARD_EXPIRED`, код `54` |
| EC-STATUS-05 | `DELETED` | Невалидный | Карта не выдаётся CMS; авторизация: `CARD_NOT_FOUND`, код `14` |

### 2.2. Срок действия

| ID | Класс | Ожидаемый результат |
|---|---|---|
| EC-EXP-01 | Месяц окончания позже текущего | Карта действительна |

| EC-EXP-03 | Месяц окончания раньше текущего | `DECLINED`, код `54` |

### 2.3. Сумма, лимиты и баланс

`A` — сумма операции; `D`/`M` — использованные суммы за день/месяц; `DL`/`ML` — дневной/месячный лимиты; `B` — доступный баланс.

| ID | Класс | Условие | Ожидаемый результат |
|---|---|---|---|
| EC-AMOUNT-01 | Положительная сумма | `A > 0` | Продолжить бизнес-проверки |
| EC-AMOUNT-02 | Нулевая сумма | `A = 0` | Ошибка валидации: в OpenAPI `amount >= 1` |
| EC-AMOUNT-03 | Отрицательная сумма | `A < 0` | Ошибка валидации |
| EC-DAY-01 | Дневной лимит не превышен | `D + A <= DL` | Продолжить проверку |
| EC-DAY-02 | Дневной лимит превышен | `D + A > DL` | `DECLINED`, код `61` |
| EC-MONTH-01 | Месячный лимит не превышен | `M + A <= ML` | Продолжить проверку |
| EC-MONTH-02 | Месячный лимит превышен | `M + A > ML` | `DECLINED`, код `61` |
| EC-BAL-01 | Средств достаточно | `A <= B` | Разрешить резервирование |
| EC-BAL-02 | Средств недостаточно | `A > B` | `DECLINED`, код `51` |

### 2.4. PAN и поиск карты

| ID | Класс | Ожидаемый результат |
|---|---|---|

### 2.5. Пагинация и фильтрация CMS

| ID | Класс | Ожидаемый результат |
|---|---|---|
| EC-PAGE-01 | `limit` не задан | Вернуть не более 50 карт |
| EC-PAGE-02 | Положительный `limit` (например, `1`, `2`, `50`) | Вернуть не более указанного количества |
| EC-PAGE-03 | `limit <= 0` | Ошибка валидации |
| EC-PAGE-04 | `offset = 0` | Начать с первой записи |
| EC-PAGE-05 | `offset > 0` | Пропустить указанное число записей |

## 3. Анализ граничных значений

### 3.1. Авторизация

| Параметр | Ниже границы | На границе | Выше границы |
|---|---:|---:|---:|
| Минимальная сумма по OpenAPI | `A = 0` → ошибка | `A = 1` → бизнес-проверки | `A = 2` → бизнес-проверки |
| Остаток дневного лимита `RD = DL - D` | `A = RD - 1` → не превышен | `A = RD` → не превышен | `A = RD + 1` → код `61` |
| Остаток месячного лимита `RM = ML - M` | `A = RM - 1` → не превышен | `A = RM` → не превышен | `A = RM + 1` → код `61` |
| Доступный баланс `B` | `A = B - 1` → достаточно | `A = B` → достаточно, баланс станет `0` | `A = B + 1` → код `51` |
| Срок действия | Предыдущий месяц → код `54` | Текущий месяц → действительна | Следующий месяц → действительна |

При `RD = 0`, `RM = 0` или `B = 0` дополнительно проверяются суммы `0` и `1`.

### 3.2. Card Management

| Параметр | Ниже границы | На границе | Выше границы |
|---|---:|---:|---:|
| Длина BIN | 5 цифр | 6 цифр | 7 цифр |
| Длина PAN | 15 цифр | 16 цифр | 17 цифр |
| `limit` списка: нижняя граница | `0` → ошибка | `1` → допустимо | `2` → допустимо |
| `offset` | `-1` | `0` | `1` |
| `count` генератора: нижняя граница | `0` → ошибка | `1` → допустимо | `2` → допустимо |
| `count` генератора: верхняя граница | `9999` → допустимо | `10000` → допустимо | `10001` → ошибка |
| Резервирование | `amount = B - 1` | `amount = B` | `amount = B + 1` |

Граница `count=10000` задана в OpenAPI (`GenerateCardsRequest`). Границы дневного и месячного лимитов проверяются при авторизации (раздел 3.1).

## 5. Попарное тестирование

### 5.1. Authorization

Модель: [model.txt](pict/model.txt); набор: [cases.txt](pict/cases.txt). Строки после заголовка соответствуют `PW-01`—`PW-15`.

| Параметр | Значения | Подготовка данных |
|---|---|---|
| `card_status` | ACTIVE, INACTIVE, BLOCKED, EXPIRED | Статус тестовой карты |
| `expiry` | PAST, CURRENT, FUTURE | Предыдущий, текущий или следующий месяц относительно даты прогона |
| `amount` | 90003, 100000, 100001 | Сумма запроса в копейках |
| `balance` | 100000, 200000 | Доступный баланс перед запросом |
| `daily_remaining` | 100000, 200000 | `DL - D` |

Предусловия PW: карта существует, CMS и БД доступны; `D=0`, `M=300000`, `DL=daily_remaining`, `ML=300000+monthly_remaining`. Использование за месяц задаётся операциями предыдущего дня того же месяца; дата прогона — после первого числа.

Шаги: подготовить отдельную карту по строке; преобразовать `expiry` в месяц, `terminal_type` в `terminalType`; выполнить общие шаги AUTH (раздел 6.1). Ответ определяется таблицей решений (раздел 4). Остальные поля запроса — из раздела 6.1.

PW покрывает пары входных значений; отдельные AUTH-кейсы проверяют ветви, которые могут быть скрыты ранним отказом.

### 5.2. Card Management

Модель [cms-model.txt](pict/cms-model.txt) и набор [cms-cases.txt](pict/cms-cases.txt) задают шесть вариантов существующего CMS-01. Все сочетания допустимы, дополнительное ограничение не требуется.

Генерация: `pict docs/practice-2/pict/cms-model.txt /o:2 /r:42 > docs/practice-2/pict/cms-cases.txt`. Шесть строк покрывают все 60 пар значений.

Для каждой строки создать отдельную карту; проверить HTTP `201`, PAN из 16 цифр с заданным BIN и корректной цифрой Луна, `ACTIVE`, срок текущий месяц + 3 года, совпадение имени, валюты, лимитов и начального баланса с запросом. Результаты фиксируются по номеру строки в evidence CMS-01; исходный Passed не распространяется на новые варианты.

## 6. Набор тест-кейсов

### 6.1. Authorization Service

Предусловия: отдельная карта `ACTIVE`, срок — будущий месяц; валюта `643`, `B=100000`, `DL=150000`, `ML=300000`, `D=M=0`, `A=90003`; CMS и БД доступны. Перед каждым вариантом восстановить исходное состояние; остальные условия должны пропускать операцию.

Для AUTH-09: `DL=200000`, `ML=400000`, `D=0`, `M=300000`, `B=500000`; для AUTH-10: `DL=ML=500000`. В AUTH-06/07 срок задаётся в тестовой БД. AUTH-12 отключает чтение CMS; AUTH-15 — только reserve. После проверки связь восстанавливается.

Общие шаги AUTH-кейсов:

1. Подготовить данные строки, сохранить B, D, M, DL и ML.
2. Отправить `POST http://localhost:8083/api/internal/authorize`. Базовые поля: `mti="0100"`, уникальный шестизначный `stan`, PAN подготовленной карты, `processingCode="000000"`, `amount=A`, `currencyCode="643"`, актуальный `transmissionDateTime` в UTC, `terminalId="TERM0001"`, `terminalType="POS"`, `merchantId="MERCH0000000002"`, `mcc="5411"`, `acquirerId="ACQ002"`, `issuerId` из созданной карты.
3. Проверить ответ, перечитать карту через CMS и счётчики в `limit_usage`: при успехе `B -= A`, `D += A`, `M += A`; при отказе они не меняются. DL и ML сохраняются.

| ID | Сценарий и тестовые данные | Ожидаемый результат |
|---|---|---|
| AUTH-01 | `D+A < DL`, `M+A < ML`, `A < B` | `APPROVED`, код `00`; RRN — 12 цифр, authCode — 6 символов `A-Z0-9`; баланс уменьшается на `A`, использованные суммы за день и месяц увеличиваются на `A`; лимиты карты не изменяются |
| AUTH-02 | Несуществующий корректный PAN | `DECLINED`, `CARD_NOT_FOUND`, код `14`; резервирование не вызывается |
| AUTH-03 | Статус `INACTIVE` | `DECLINED`, `CARD_INACTIVE`, код `05` |
| AUTH-04 | Статус `BLOCKED` | `DECLINED`, `CARD_BLOCKED`, код `05` |
| AUTH-05 | Статус `EXPIRED` | `DECLINED`, `CARD_EXPIRED`, код `54` |
| AUTH-06 | `ACTIVE`, expiryDate — предыдущий месяц | `DECLINED`, `CARD_EXPIRED`, код `54` |
| AUTH-07 | `ACTIVE`, expiryDate — текущий месяц | Проверка срока пройдена; решение зависит от лимитов и баланса |
| AUTH-08 | `B=ML=500000`, `DL=150000`, `D=M=0`; параметризованный: `A = RD-1`, `RD`, `RD+1` | Первые два значения одобрены; третье — `DECLINED`, `EXCEEDS_AMOUNT_LIMIT`, код `61` |
| AUTH-09 | Параметризованный: `A = RM-1`, `RM`, `RM+1` | Первые два значения не отклоняются по месячному лимиту; третье — код `61` |
| AUTH-10 | Параметризованный: `A = B-1`, `B`, `B+1` | Первые два значения допустимы; третье — код `51` |
| AUTH-11 | Одновременно `D+A > DL` и `A > B` | По строгому порядку проверок код `61` |
| AUTH-12 | CMS недоступен при чтении карты | `DECLINED`, `ISSUER_TIMEOUT`, код `05` |
| AUTH-13 | `B=DL=ML=500000`, `D=M=0`; два запроса по `90003` в одну секунду | Оба запроса одобрены; оба RRN уникальны и соответствуют формату из ТЗ |
| AUTH-15 | CMS отвечает на чтение карты, но недоступен при reserve | `DECLINED`, `ISSUER_TIMEOUT`, код `05`; баланс и использованные суммы не изменены |

### 6.2. Card Management Service

Предусловия: CMS — `http://localhost:8081`, BIN `400000` существует. Карта создаётся через `POST /api/cards`: `cardholderName="IVAN IVANOV"`, `currencyCode="643"`, `dailyLimit=150000`, `monthlyLimit=300000`, `initialBalance=100000`. PAN берётся из ответа. Для генератора нужны пять существующих BIN.

Шаги: подготовить данные, выполнить запрос из строки, проверить ответ и состояние карты через GET. Каждый параметризованный вариант выполняется независимо.

| ID | Сценарий и тестовые данные | Ожидаемый результат |

| CMS-02 | `GET /api/cards/{pan}` созданной карты | `200`, поля совпадают с созданными |
