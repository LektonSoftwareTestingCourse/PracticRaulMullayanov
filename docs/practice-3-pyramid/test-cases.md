# Практика 3 — тест-кейсы и анализ пирамиды

Карта системы: [А1 — Context](architecture/01-context.md), [А2 — Container](architecture/02-containers.md), [А3 — Component](architecture/03-components.md), [А4 — Sequence](architecture/04-sequences.md), [А5 — RabbitMQ](architecture/05-rabbitmq.md), [А6 — состояния](architecture/06-states.md).

## Часть (б). Новые тест-кейсы

Уровень выбирается по объекту проверки:

- `unit`: вызов класса в памяти, внешние зависимости заменены двойниками; без HTTP-сервера, PostgreSQL и RabbitMQ.
- `api`: запрос/ответ одного сервиса через HTTP; проверяется внешний контракт, смежные сервисы изолированы. БД может быть частью тестового запуска, но её таблицы не служат oracle.
- `integration`: реальное соединение с PostgreSQL/RabbitMQ либо доставка между компонентами; проверяются данные и побочные эффекты.
- `e2e`: платёж через публичный Gateway с настоящими Switch, Authorization, CMS и журналом/брокером; проверяется итог всей цепочки.

API-кейс нельзя обосновать одним unit-вызовом контроллера, а интеграцию с брокером — Mockito `verify(send)`. Уровень относится к описанной процедуре, а не к имени будущего файла.

### Общие данные и правила выполнения

В каждой строке используется отдельная карта / UUID / STAN. Для HTTP-запроса авторизации базовые данные: `mti=0100`, `stan=123456`, PAN созданной карты с BIN `400000`, `processingCode=000000`, `amount=90003`, `currencyCode=643`, текущее `transmissionDateTime` в UTC, `terminalId=TERM0001`, `terminalType=POS`, `merchantId=MERCH0000000002`, `mcc=5411`, `acquirerId=ACQ002`, `issuerId=ISS001`. Между сценариями STAN заменяется, тестовые данные сбрасываются. Денежные значения — в копейках, сравнение без округления.

Для успешного платежа карта `ACTIVE`, срок будущего месяца, `B=100000`, `DL=150000`, `ML=300000`, использованные суммы `D=M=0`. Уровень API CMS обращается **напрямую к CMS**, чтобы кеш Gateway не искажал перечитывание карты. E2E также проверяет финансовое состояние прямым чтением CMS / БД.

Async-проверки используют polling каждые 100 ms до 10 s, если в строке не указан другой deadline. Это бюджет тестового ожидания, а не обещанный SLA системы. Корреляция — UUID сообщения для Logger, `pan+rrn+тип события` для reserve/rollback Notification. Начальные записи фиксируются до действия; посторонние события не засчитываются. Перед fault injection сохраняются настройки; после кейса восстанавливаются сеть, listeners и данные. Эти сценарии выполняются на отдельном тестовом стенде.

В «Источник» указана техника тест-дизайна. Связь с требованием дана отдельно: именованный пункт локального ТЗ либо реализованный контракт класса. У ТЗ нет единого реестра уникальных requirement ID; `P3-*` ниже — идентификаторы **кейсов**, а не вымышленные номера требований.

HTTP POST, авторизация и расчёт комиссии происходят до `t0` и в измерение не входят. Прокси не задерживает отправку сообщения, а изменяет только confirm. Интервал 2000–2500 ms проверяет timeout 2 s и допускает до 500 ms на обработку и планирование; ранняя компенсация в варианте без confirm считается ошибкой. Для NACK проверяется отдельный интервал 0–500 ms после получения отказа: ожидание двух секунд не требуется. Допуск 500 ms — технический бюджет проверки на стенде, а не отдельное требование ТЗ о SLA. Наблюдатели не подменяют RabbitTemplate или HTTP-клиент и не меняют бизнес-логику.

### Почему эти уровни достаточны

U01/U02 проверяют функцию без сети; U03 добавляет контроль отсутствия финансовых побочных вызовов к AUTH-04; U04 проверяет счётчик публикаций без реального времени. U05 проверяет контрольную цифру и генерацию PAN с независимым ожидаемым результатом; U06 — переход удержания и запрет повторного возврата на доменных объектах. Для U05/U06 HTTP, БД и брокер не нужны. A01 проверяет HTTP-десериализацию и error contract, A02 — внешний контракт частичного обновления, A03 — контракт отдельного справочника. I02/I03 требуют настоящей очереди и сохранения данных; I04 проверяет реальный AMQP-протокол при управляемых смежных HTTP-контрактах. E01/E02 оставлены на всю цепочку из-за риска частичного списания / компенсации.

В новом наборе **6 unit, 3 api, 3 integration и 2 e2e**. Дополнительные интеграционные кейсы P3-I01 (смена дня/месяца в SQL) и P3-I05 (DLQ/TTL) исключены; вместо них добавлены P3-U05/U06 с другими объектами проверки. Идентификаторы оставшихся кейсов сохранены. Проверки реальной доставки, outbox и publisher confirm остаются интеграционными: подстановка зависимостей не доказывает эти свойства.

Это 14 новых **описаний** кейсов, четыре уровня, sync и async пути. Параметры / варианты внутри строки не увеличивают число кейсов. Семантика ACTIVE/BLOCKED встречается в практике 2, но новые U03/A02 имеют другой объект проверки: отсутствие вызова зависимости и обратимый PATCH статуса. Копия прежнего HTTP/SQL-прогона за новый кейс не засчитывается.

Дополнительные пробелы карты: API MTI 0400 не поддерживается; consumer retry «3 доставки» не доказан настройкой `x-max-delivery`; создание карты и outbox не имеют очевидной общей локальной транзакции; Notification не дедуплицирует события. После сокращения набора смена дня/месяца в SQL и реальное поведение DLQ/TTL также не покрыты отдельными новыми кейсами; unit-проверки их не заменяют. Для этих областей нужны следующие интеграционные кейсы. Таблица не объявляет полное покрытие всех требований.

Общие шаги AUTH включают запрос в настоящий Authorization, CMS и **прямую проверку `limit_usage` SQL**. Поэтому полный существующий кейс классифицируется как integration, даже если отдельную его проверку статуса можно выделить в unit. PW выполняются по тем же шагам. Большинство CMS-кейсов проверяет ответ и состояние через HTTP GET; для их описанного oracle прямой SQL не обязателен, поэтому выбран api. ### Почему получилось такое распределение

Ориентир 70/20/10 не достигнут. Основная причина — исходная практика 2 была ручной проверкой HTTP-контрактов и финансового состояния Authorization/CMS, поэтому 44 старых кейса уже относятся к api/integration. Их процедуры и уровни сохранены: простое переименование потеряло бы SQL / CMS assertions. В новом наборе unit-кейсов шесть — это самая большая группа новых проверок; они проверяют локальные решения, контрольную цифру PAN и доменные переходы. Три интеграционных кейса оставлены для доставки в Logger, outbox → Notification и отказа publisher confirm.

Для микросервисов API/integration закономерно важны: корректность каждого класса ещё не доказывает формат JSON, настоящий PostgreSQL upsert, удержание при удалённом вызове, AMQP-routing и сохранение потребителем. Особенно опасны частичные результаты — деньги зарезервированы, а журнал не появился; деньги возвращены, а лимиты остались израсходованными.

E2E оставлено два: успешный платёж и компенсация при отказе публикации. Их высокая стоимость оправдана финансовым риском всей цепочки. Варианты PAN, статуса, лимитов, pagination и формат JSON дешевле проверять ниже; поэтому они не размножаются в E2E.

Риска **ice-cream cone** (преобладания E2E) здесь нет: E2E составляет 3,448%. Доля unit в общей таблице всё ещё невелика — 10,345%, поскольку старые 44 кейса используют инфраструктуру. Среди новых кейсов локальные проверки преобладают, а интеграционные оставлены для свойств настоящей очереди и потребителей. При последующей автоматизации стоит выделять независимые доменные проверки из существующих сценариев, сохраняя необходимое покрытие SQL / HTTP / AMQP. Новые описания не являются уже реализованной автоматизацией, а число кейсов само по себе не характеризует время и стоимость прогона.

Контрактные проверки распределены неравномерно: практика 2 сосредоточена на CMS и Authorization. A01/A03 расширяют Gateway/BIN, I04 — контракт компенсации Switch. Ещё остаются пробелы полных контрактов ошибок смежных сервисов, смены периода лимитов в SQL, DLQ/TTL, consumer retry, атомарности create+outbox, MTI 0400 и дедупликации Notification. Сокращение двух интеграционных кейсов уменьшает стоимость будущего набора за счёт отложенного покрытия этих областей; общее число описаний остаётся 58.
